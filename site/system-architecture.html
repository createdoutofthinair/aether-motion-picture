The protocol boundary

Model Context Protocol (MCP) standardizes how an AI application discovers and exchanges context with an MCP server. It defines protocol messages and transports; it does not define how a host uses an LLM, how a production job is scheduled, or how an external provider bills it. The official MCP architecture overview describes these boundaries.

An MCP host is the application coordinating the work. The host creates an MCP client for each server it connects to; that client maintains the server connection and relays requests and results. An MCP server is the program exposing protocol capabilities. A server may run locally over standard input/output (STDIO) or remotely over Streamable HTTP. “Server” describes its protocol role, not its physical location.

AI host
  ├─ MCP client ── transport ── MCP server A
  └─ MCP client ── transport ── MCP server B

The MCP data layer carries discovery and JSON-RPC messages. The transport layer establishes the communication channel and, for HTTP deployments, handles transport authorization. A host may also have native tools, command-line runtimes, file access, or sub-agent coordination that are not MCP servers. Do not infer that every available capability is an MCP tool.

Tools, resources, prompts, skills, and files

These names refer to different things. MCP defines tools, resources, and prompts as server capabilities; “skill” and “workspace file” are separate runtime artifacts in this production workflow.

Item Role Example in an audiovisual workflow
MCP tool A schema-defined operation that can perform an action when called A connected media server exposing a generation or query operation
MCP resource Data a server exposes to give the host context, identified by a URI A server-provided project record or document
MCP prompt A server-provided reusable message template A server template for a structured task
Local skill Instructions and supporting references that teach an agent how to use a runtime The Kling CLI skill explains capability discovery, account checks, submission, and polling
Workspace file A durable local artifact read or written by an authorized process A shot manifest, approved still, MP4, or results CSV

The MCP tools specification, resources specification, and prompts specification define the first three rows. A local skill does not become a server capability merely because it describes a tool call. Likewise, a file on disk is not automatically an MCP resource; a server must explicitly expose it as one.

The Kling CLI lane used for this production

For this batch, video creation ran through the pinned Kling Global CLI package at version 0.2.1. The CLI skill states that it owns browser OAuth and that this runtime does not register a host MCP server. The workflow used CLI commands such as tool_list, who_am_i, account, image_to_video, and query_tasks; it did not call the Kling API directly or use a Kling MCP tool.

The observed production lane can be summarized this way:

Codex host ── local shell ── pinned Kling CLI 0.2.1 ── provider service
     │                              │
     │                              └─ owns provider browser OAuth
     └─ workspace files: stills, manifest, ledgers, downloaded MP4s

MCP-connected services are a separate lane and were not the Kling
video-generation interface used for this batch.

This distinction matters when troubleshooting. An MCP tools/list response describes tools exposed by an MCP server. Kling who_am_i describes the current CLI account’s available Kling models and arguments. Those are different discovery surfaces, with different credentials and capability declarations. Do not substitute one surface’s capability list or authorization token for the other.

The production dependency chain was:

  1. Read the shot treatment and approved still.
  2. Read one manifest row with its prompt and duration.
  3. Discover the live CLI model and its legal arguments.
  4. Check current provider credits, then submit once.
  5. Poll the returned task ID to terminal status.
  6. Refresh the selected work and download its authorized watermark-free URL.
  7. Record and verify the local MP4.

Observed and reusable

Observed: the Kling video lane used the pinned CLI and its live model declaration, while the stills and manifests remained local workspace files. The consolidated results ledger preserved the selected generation ID, work index, status, result link and attempt notes. A trace ID, when returned, belongs in the private per-attempt record.

Reusable: write down the integration boundary before work starts. Name the host, client or CLI, server/provider, auth surface, durable input artifacts, and output ledger. Then route each operation through its intended interface and retain evidence from that interface.
