Authorization boundaries and session verification

MCP authorization is transport-specific

The MCP authorization specification covers restricted servers over HTTP transports. In that flow, the MCP client obtains an access token for a protected resource and sends it in the HTTP Authorization header. The server validates the token for its own audience. The MCP authorization specification treats this as transport authorization, separate from the tool’s business logic.

Authorization is optional for MCP implementations. The specification says HTTP-based implementations that support authorization should follow its OAuth flow; STDIO implementations should not use that HTTP authorization flow and instead obtain credentials from the environment. The correct mechanism depends on the server and transport.

Provider CLI OAuth is a separate boundary

The pinned Kling CLI’s local skill says the CLI owns its browser OAuth flow. If that flow opens Microsoft Edge, Edge is the consent surface; being signed into an Edge profile alone does not prove that the Kling CLI has an authorized provider session. Likewise, an MCP host’s token does not authorize a separate provider CLI.

When Edge opens, complete consent for the provider there and let the CLI finish its own callback. Do not copy an Edge cookie or OAuth token into a shell command or an MCP configuration. The browser is an authentication interface; the CLI’s own post-login response is the evidence that its session is usable.

Keep the sequence simple:

  1. Run the exact pinned CLI version required by the installed skill.
  2. If the CLI reports that it is unauthorized, run its documented login command and complete the provider consent flow in the browser it opens.
  3. Verify the resulting CLI session with who_am_i; confirm that the command returned complete JSON and that the requested tool and model appear in the current account’s live capability list.
  4. Before each paid submission, run account and confirm that the balance field is present and positive. Stop for missing or nonpositive balance information or known insufficiency.

The pinned command shape for a locally installed Kling CLI is:

npm exec --yes --registry=https://registry.npmjs.org --package=@klingai/cli-global@0.2.1 -- kling login --skill-name kling-ai-cli --skill-version 1.1.2
npm exec --yes --registry=https://registry.npmjs.org --package=@klingai/cli-global@0.2.1 -- kling who_am_i --skill-name kling-ai-cli --skill-version 1.1.2 --quiet

Use login only when the CLI reports that it is unauthorized. Capture who_am_i privately if its response is large; inspect only the success state and the tool/model declarations needed for the job.

Never inspect browser cookies, copy tokens out of the browser, paste credentials into a terminal, or route a provider token through an unrelated MCP server. The login command, rather than the user’s browser profile, owns the provider session.

Capability verification is not authorization verification

who_am_i answers whether the CLI can see an account and which models/arguments it currently exposes. account answers what balance or membership data the provider returns. Neither proves that a specific job succeeded. After an accepted request, query_tasks <generationId> establishes job state; a completed task with a successful indexed video work establishes a usable result.

In this production, the first sandboxed CLI call hung before returning. No job was submitted from that attempt. Once the pinned runtime was allowed to reach the registry, version and live capability checks succeeded and a fresh account check returned a positive balance. The lesson is to preserve the complete command output privately and diagnose a runtime or registry issue before treating the provider session as absent.

Safe session evidence

For a handoff, report only facts needed to proceed: pinned CLI version, whether live capability discovery completed, whether the account check returned a usable positive balance, and the time of the check. Do not include account identity fields, tokens, cookies, signed URLs, or entire who_am_i responses in chat or shared logs. MCP HTTP authorization tokens belong in the transport’s Authorization header and must be validated for the specific resource server; the MCP authorization spec says not to place access tokens in a URI query string.

Reusable check: a browser consent page is not the verification step; the CLI’s own successful response is. A positive balance is a preflight result, not an exact cost quote. If the provider does not return an exact cost for the requested settings, do not invent one.
