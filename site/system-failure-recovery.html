Task states, lost responses, and safe recovery

On this pageAccepted is not completedInterpret polling carefullyLost submission responsesSanitized recovery examples

Accepted is not completed

An image-to-video command may return an accepted task ID before any video exists. Record the generation ID immediately, then use the pinned CLI’s query_tasks <generationId> command until the task is terminal. A task-level COMPLETED state is not enough if its selected work is missing, failed, or the wrong content type. Require the selected indexed work to complete as a video.

generationId identifies the provider task. taskTraceId groups related CLI operations; it does not identify a task, provide history lookup, or prevent a duplicate charge. Preserve the original works[] index exactly as returned, including zero-based index 0 when that is what the provider returns.

Interpret polling carefully

The CLI can time out its bounded poll while the task itself remains RUNNING or QUEUING. In that case, keep the same task ID, wait, and query again. A poll timeout is not terminal failure and is not permission to submit another generation.

Capture complete stdout, stderr, and exit code privately before parsing. Some timed-out query responses can have a nonzero CLI exit code while still containing a valid JSON body that reports timedOut: true and the current task state. Read both the exit code and the structured body; never expose signed URLs from result output during diagnostics.

Lost submission responses

If a paid submission returns an unparseable response or no generation ID, creation may have succeeded even if the local command failed. Do not replay the command. Preserve the original prompt/settings and diagnostic files, mark the row UNKNOWN_CREATION_STATE, and report that no task lookup is available by trace ID. Request explicit authorization before any replacement, including acceptance that a duplicate charge may be possible.

If a generation ID was returned, only query that ID. If a query returns a terminal provider failure, preserve the exact terminal status and error summary, and do not automatically retry. A revised prompt, changed model, or replacement request is a new paid operation and requires authorization.

Sanitized recovery examples

Observation Correct ledger state Next action
COMPLETED, work 0 is a successful video COMPLETED Refresh the same task and select work 0 for delivery
Poll times out, task says RUNNING RUNNING Query the same generation ID later
Submit response has no usable task ID UNKNOWN_CREATION_STATE Stop; do not retry without explicit duplicate-risk approval
Work 0 is absent or is an image/cover UNUSABLE_RESULT Record it; do not download the cover as the video
Terminal provider error FAILED Report exact safe error summary; wait for a user-authorized next step

The MCP authorization specification governs MCP transport authentication, not a provider CLI’s task lifecycle. Keep those recovery paths separate: an expired MCP token may require reauthorization; a queued Kling generation requires polling its provider generation ID.
