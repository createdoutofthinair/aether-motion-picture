Approval, billing, and the jobs ledger

On this pageTreat the manifest as the production contractApproval before paid workBilling and audit trailSanitized ledger example

Treat the manifest as the production contract

The clip manifest is the source of truth for the still filename, prompt, duration, and story beat. Do not silently swap the still, rewrite the prompt, change the model, or alter output settings while submitting. Keep the actual provider result in a separate ledger so the creative brief and the job record remain independently reviewable.

A useful manifest row contains:

Field Purpose
Clip label and still filename Identifies the exact job input
Prompt and duration Defines requested motion and timing
Settings Model, aspect ratio, resolution, and output count
Reference role Confirms the still is the first frame or another supported slot

The result ledger should add the generation ID, trace ID, task terminal status, original works[] index, content type, returned result link, and failure note. A download ledger should record the task ID, terminal status, local path, byte count, refreshed watermark-free URL, and validation failure, if any.

Approval before paid work

Before the first paid request, show the user the final model, prompt summary, duration, aspect ratio, resolution, output count, reference role, and actual billing information when the provider exposes it. Obtain explicit confirmation for the paid settings. If the user already confirmed unchanged settings for the batch, subsequent jobs with the same settings need not be reconfirmed; a material change needs a new approval.

Immediately before each paid submission, run the pinned CLI’s account check. Stop if the balance is missing, zero or negative, or the provider reports insufficient credits. A positive balance is a useful guard but does not prove that it covers the entire batch when exact per-job cost or conversion to an external API-unit estimate is unknown. Keep estimates and observed account credits in separate columns or notes; never present one as a conversion for the other.

Billing and audit trail

Paid generation is an external side effect. The ledger must let a reviewer answer:

  1. Which approved still and prompt were submitted?
  2. Which model and settings were used?
  3. Which account preflight immediately preceded the call?
  4. What task and trace IDs did the CLI return?
  5. Did the task finish, and which video work was selected?
  6. Was a duplicate submission attempted?

Keep the trace ID as a grouping label, not as a task lookup key or idempotency token. The generation ID is the identifier used to query a specific task. Do not remove failed or ambiguous rows; record their state and why the workflow stopped.

The following is a format example only. IDs are placeholders; it contains no provider URL or account data.
