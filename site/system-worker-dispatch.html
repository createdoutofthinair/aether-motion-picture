Hands-on guide to dispatching media workers

On this pageStart with one coordinator and one shared ledgerDispatch in dependency-safe wavesReusable dispatch briefWorker stagesReporting envelopePolling, retries, and slot release

This chapter is an operator recipe for splitting a media manifest across workers without losing track of dependencies, paid requests, or deliverables. One coordinator owns the shared plan and ledger. Workers own only the exact rows assigned to them.

Start with one coordinator and one shared ledger

The coordinator owns the approved manifest, the total authorized budget, the global active-slot limit, the assignment map, polling schedule, and final reconciliation. Workers do not reserve budget for each other, change settings, or take rows from another worker. Keep one durable ledger as the source of truth; a worker may keep a local scratch log, but the coordinator reconciles every state change into the shared ledger.

Use one row per paid attempt. A useful ledger includes:

Field Purpose
Clip label and attempt Stable identity, including suffixes such as 056A and 056B
Owner and dependency One worker and any required still, reference, or approval
Slot state FREE, RESERVED, ACTIVE, UNKNOWN_CREATION, or RELEASED
Budget state Authorized, reserved, spent/estimated, or stopped
Account check Timestamp and positive/valid result for this request
Submission state Not started, accepted, terminal, or unknown
Task identifiers Generation ID and trace ID, stored in the project ledger
Result and QA Terminal state, selected work index, local file, and validation

The coordinator grants a slot before work begins. After acceptance, keep it occupied until a terminal state. If the response is ambiguous, keep the reservation and mark UNKNOWN_CREATION; do not free the slot merely because the worker cannot see a task ID.

Dispatch in dependency-safe waves

Organize work around prerequisites instead of assigning arbitrary batches all at once:

  1. Freeze the inputs. Approve the treatment, manifest rows, prompts, settings, budget, and concurrency policy. Confirm every referenced file exists and assign each row to one owner.
  2. Approve identity anchors. If a character reference or continuity still is missing or unapproved, resolve it before releasing shots that depend on it.
  3. Generate independent stills. Backgrounds, empty locations, and other frames with no character dependency can move while the identity anchor is being reviewed.
  4. Release dependent stills. Once the anchor is approved, workers generate the character shots using that exact reference and report the still path for review.
  5. Animate approved stills. A video job is eligible only after its exact first-frame still has been approved and matched to its manifest row.
  6. Deliver and reconcile. Refresh the original task result, select the specified work index, use only an eligible watermark-free result, download, validate, and update the shared ledger.

For example, the project’s captain continuity anchor is still 004_Dark_Has_Begun_Captain_Reference.png. If that reference has not been approved, hold captain-dependent images such as the corridor/shoulder view, the captain at the viewport, visor or face close-ups, reflective-face shots, foreground captain frames, and captain-at-hull frames. In the numbered treatment these include character-dependent candidates such as 019, 022, 024–029, 030–031, 034, 042, and 045–050; check each manifest description because a number alone does not prove dependency. Independent space or landscape shots such as 020, 021, or 023 may proceed only if their actual frame does not rely on captain identity. After the anchor is approved, release the character stills; after each still is approved, release only its matching video row.

Parallel still generation with GPT imagegen

When the artist explicitly requests workers and GPT image generation, the coordinator freezes the approved visual bible, references, dimensions, numbered prompts and credit/spend policy, then assigns disjoint shot-ID ranges. Every worker receives the same reference files with their roles and may write only its assigned filenames. Use one built-in imagegen call for each distinct shot; several variants of one prompt do not replace separate story frames. Keep shots that depend on a specific predecessor pose or prop state in a later wave until that reference frame is approved.

Built-in GPT imagegen saves to Codex’s generated-images directory by default. Each worker reports its shot ID, prompt, input references, generated source path and project copy. The coordinator copies accepted results into the numbered still folder, checks adjoining shots and recurring identities, confirms the final 1920×1080 dimensions, and updates the central manifest. The Kling CLI task-ID, polling and watermark-free-download procedure below applies only to Kling jobs; do not invent Kling IDs for built-in imagegen results.

Prevent reference-composition carry-over

A reference can pull an image back to its original camera angle, group arrangement, background or prop placement even when it was supplied for identity. Label every input by role and state what to preserve and what to ignore. For example, use a cast frame for faces and wardrobe only, and a separate location image for the new shot’s setting and composition. If a full cast lineup keeps recreating its original layout, use a subject-only portrait or tight, composition-neutral identity crop; for distant silhouettes, omit an unnecessary cast lineup. Pilot a difficult composition first. Reject a frame that copies the wrong layout, correct the reference roles or prompt, and inspect a new result before releasing the rest of that batch.

Reusable dispatch brief

Copy this brief for each worker and fill every bracketed field before assignment. The coordinator must record the same reservation and ownership in the shared ledger.

Assignment: [batch or wave name]
Owner: [worker name]
Exact clip labels: [explicit labels; include suffixes]
Allowed files: [manifest, still directory, reference files]
Allowed writes: [worker result ledger and assigned output paths]
Dependency gate: [approved still/reference IDs; state what remains blocked]
Prompt source: [manifest path and exact row identifiers]
Settings: [model, duration per row, resolution, aspect ratio, output count]
Budget authorization: [shared reservation identifier and amount/limit]
Concurrency: [shared global cap, this worker's allocation, reservation owner]
Before every paid request: obtain one shared slot, then run a fresh account check.
Submission: use the pinned approved CLI, exact assigned still and prompt, once.
Polling: query only the accepted task ID; retain the slot until terminal.
Retry rule: never retry an accepted or ambiguous request. Return uncertainty to coordinator.
Reporting: return the required envelope for every row, including failures.
Stop conditions: missing input, blocked dependency, invalid account check, insufficient
credits, CLI error, or ambiguous creation state. Stop the affected row and report it.

Do not treat a worker’s local cap as the global cap. The coordinator’s slot ledger is the authority for shared capacity and budget reservations. A local queue must never submit until its shared reservation is granted.

Worker stages

Each worker follows this same sequence for each assigned row:

  1. Validate. Check label, prompt, input image, dimensions, dependency approvals, and exact settings against the manifest. Report mismatches before any paid call.
  2. Reserve. Request a shared budget reservation and active slot. Record the grant in the ledger before proceeding.
  3. Check the account. Immediately before submission, run the approved account check. Stop if it fails, is missing, nonpositive, or indicates known insufficiency. The check is evidence of current account state, not a lock on credits shared with other workers.
  4. Submit once. Use the pinned CLI and exact row inputs. Capture complete local stdout, stderr, and exit code securely. Do not expose credentials, signed URLs, or private response data in routine reports.
  5. Track the task. Save the returned generation ID and trace ID. Query that generation ID until terminal. A trace ID helps correlate events; it is not a safe retry key.
  6. Report terminal state. Send the coordinator the result envelope, including failures and unresolved uncertainty. Keep the slot occupied until the coordinator ledger reflects terminal state.
  7. Deliver. For successful work, refresh the indexed result from the original task, download only an allowed watermark-free result, validate the local media, and report path and QA outcome. Do not substitute a watermarked link if the allowed result is absent.

Reporting envelope

Report one structured envelope per clip, including rows that stopped before submission. Never put signed result URLs in chat or terminal output. If the coordinator needs a result link in a restricted ledger, store it there with the correct access controls.

{
  "clip": "056A",
  "attempt": 1,
  "worker": "worker-b",
  "stage": "terminal",
  "generationId": "SYNTHETIC_GENERATION_ID_056A",
  "traceId": "SYNTHETIC_TRACE_ID_056A",
  "status": "COMPLETED",
  "workIndex": 0,
  "slotState": "RELEASED",
  "localFile": "BlackStar_Videos/056A_Synthetic_Name.mp4",
  "qa": { "bytes": 1234567, "ftyp": true, "dimensions": "1920x1080" },
  "watermarkFreeResult": "stored in restricted ledger; redacted in this example",
  "failure": null
}

These IDs and file details are synthetic. The envelope shows the shape of a handoff, not a real job record.

Polling, retries, and slot release

The coordinator schedules polls so that workers do not hammer the service or all query the same job. Set a reasonable interval, such as 60 seconds, then increase it for long-running jobs. A poll timeout with a nonterminal state such as RUNNING or QUEUING means schedule another query for the same task ID; retain its slot and budget reservation.

When submission is accepted, do not retry it. When a response is lost or creation status is unclear, mark UNKNOWN_CREATION, preserve the local evidence, keep the slot reserved, and ask the coordinator to reconcile. Never submit a second request merely because the first response omitted an ID. A retry requires explicit authorization, a new attempt row, a new slot and budget reservation, and a fresh account check. A terminal failure is still a recorded attempt; it is not automatic permission to retry.

The coordinator releases a slot only after a confirmed terminal state and records the result or failure. If a result link expires, refresh the original task’s indexed work rather than generating again. If the watermark-free result is unavailable, record the limitation and stop that delivery row without using a watermarked fallback.
